3. TARGET MIGRATION ARCHITECTURE

Unless repository evidence proves a better existing mechanism, the desired end state is:

Drizzle schema
      ↓
Versioned generated migration SQL
      ↓
Reviewed committed migrations
      ↓
Controlled deployment
      ↓
Database

Startup DDL should not remain a permanent competing schema authority.

However:

Do not remove startup DDL immediately if existing deployments depend on it.

Develop a safe transition strategy.

Possible staged approach:

Stage A

Create canonical versioned migration support.

Stage B

Reconcile current production/fresh-schema parity.

Stage C

Move remaining functions/triggers/indexes/RLS into committed migrations.

Stage D

Reduce startup DDL to harmless compatibility/bootstrap checks.

Stage E

Retire duplicate DDL only after deployment evidence proves it safe.

Adapt this to actual repository conditions.

---

6. OBJECTIVE D — EXISTING DATABASE COMPATIBILITY

Verify that the migration strategy is safe for an existing Calora database.

Look specifically for:

- non-null additions;
- renamed columns;
- changed types;
- unique constraints over existing data;
- cascading deletions;
- default-value differences;
- existing duplicate values;
- schema drift based on database age.

Prefer:

- additive changes;
- nullable transitional fields;
- backfill before enforcement;
- reversible migrations.

Do not introduce an unsafe migration simply to make schemas look cleaner.

11. SERVICE ROLE REVIEW

Identify every server path using elevated database credentials or service-role behavior.

For each, document:

- why elevated access is needed;
- which routes use it;
- whether user identity is independently validated;
- whether user ownership is enforced before query execution;
- whether accidental cross-user queries are possible.

RLS does not protect requests performed with privileged bypass credentials in the same way as normal authenticated requests.

Treat this carefully.
