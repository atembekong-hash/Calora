FINAL PHASE 2B ACTIVATION-READINESS REVIEW

Mission

Perform an independent, adversarial, evidence-driven final activation-readiness review of Calora Coach Fact Context Phase 2B.

The purpose is to determine whether the dormant Fact Context architecture is genuinely safe for a future tightly controlled cohort activation.

This task does NOT authorize activation.

Do not trust previous reports, implementation claims, comments, test names, or intended architecture as proof.

Inspect the current repository and verify every material claim independently from code, configuration, database behavior, tests, runtime paths, and reproducible evidence.

Start from the current authoritative repository state.


---

1. Establish the exact current state

Before reviewing readiness:

verify repository/branch state;

verify relevant commits are present;

inspect the Phase 2B reports and remediation history;

identify every Phase 2B client, server, database, rollout, consent, lifecycle, security, and test component;

construct the actual request/data-flow from Coach UI to provider and back;

identify every gate capable of permitting or denying Fact Context.


Confirm independently that the current production-safe state is:

client Fact Context gate OFF;

server Fact Context gate OFF;

named cohort empty/disabled;

no account eligible;

Fact Context allowlist unchanged;

legacy Coach remains operational;

Longitudinal Intelligence remains OFF.


If any of these statements is false, STOP and report it as a blocker.


---

2. Verify the real database authority

Independently prove that Coach Fact Context durable consent belongs to the canonical managed PostgreSQL/Drizzle architecture.

Trace the complete production deployment path.

Verify:

canonical schema ownership;

migration/deployment mechanism;

DATABASE_URL target;

no competing active Supabase DDL;

production deployment can actually create/update the consent schema;

schema and runtime expectations agree;

constraints survive deployment;

deletion cascade is real;

metadata-only storage is maintained.


Inspect the database schema rather than relying only on ORM declarations.

Test where safely possible.

Any ambiguity over which database owns consent is an activation blocker.

Hard boundaries

This task is review and validation only.

Do not repair substantive defects during the review.

Small instrumentation or test harness changes necessary to obtain evidence are permitted, but they must not alter production behavior.

If a defect is discovered, document it.

Do NOT activate Fact Context.

At completion the repository/runtime must retain:

Server gate: OFF

Cohort: EMPTY / DENY ALL

Allowlist: UNCHANGED

Legacy Coach: AVAILABLE

Longitudinal Intelligence: OFF

Physical-device and accessibility validation remain deferred. Do not falsely mark them passed.
