CALORA PRODUCTION READINESS MASTER AUDIT

Mission

Act as an independent senior engineering, security, QA, mobile, backend, DevOps, and product-readiness team conducting a forensic production audit of Calora, a React Native / Expo mobile application for Android and iOS.

Your objective is simple:

«Determine, through evidence and real execution, whether Calora is genuinely safe, stable, secure, reliable, and ready for public production release.»

Do not assume that any existing implementation works.

Do not trust previous agent reports, comments, TODO status, test claims, or apparent code completeness without verification.

Do not optimize for finding a few obvious bugs.

Attempt to uncover everything that could reasonably cause:

- crashes
- broken user journeys
- incorrect nutrition data
- authentication failures
- unauthorized data access
- payment failures
- subscription entitlement errors
- lost user data
- privacy violations
- exposed credentials
- API failures
- poor performance
- broken layouts
- unusable controls
- platform-specific failures
- App Store or Google Play rejection
- production incidents

Treat this as the final engineering investigation before real customers receive the application.

---

PHASE 0: PROTECT THE PROJECT

Before modifying anything:

1. Inspect the repository structure.
2. Identify the active branch and current commit.
3. Record the baseline state.
4. Identify build and deployment configuration.
5. Identify production, staging, development, and local environments.
6. Identify all environment variables and secrets by NAME only.
7. Never expose secret VALUES in reports or logs.
8. Determine whether tests can safely interact with external services.
9. Do not perform destructive operations against production data.
10. Do not trigger a production deployment or mobile build unless explicitly required and safe.

Create a recoverable checkpoint before remediation.

Audit first.

Fix second.

Never make large speculative rewrites merely to make the architecture look cleaner.

PHASE 20: DEFECT REGISTER

Every confirmed issue must receive a unique identifier.

Use severity:

P0 BLOCKER

Catastrophic release blocker.

Examples:

- serious security compromise
- broad unauthorized data exposure
- payment system fundamentally broken
- application unusable for major users
- destructive data corruption

P1 CRITICAL

Major production failure requiring correction before release.

P2 HIGH

Significant defect that materially harms reliability, security, correctness, or important UX.

P3 MEDIUM

Real defect with limited impact or practical workaround.

P4 LOW

Minor defect, polish issue, or low-risk improvement.

For every defect record:

- ID
- title
- severity
- affected flow
- affected platform
- file/component
- reproduction steps
- expected behavior
- actual behavior
- evidence
- likely root cause
- confidence level
- recommended correction
- regression risk
- verification method

Separate:

CONFIRMED

from

SUSPECTED / REQUIRES VERIFICATION

Never inflate the report with speculative defects.

---

PHASE 21: REMEDIATION

Only after the initial audit and defect register are sufficiently complete should remediation begin.

Fix issues in this order:

1. P0
2. P1
3. P2
4. P3
5. P4 when justified

For every fix:

1. reproduce the defect
2. identify root cause
3. design the smallest safe correction
4. inspect dependencies
5. implement
6. test locally
7. test the original reproduction case
8. test adjacent functionality
9. run regression tests
10. record evidence

Avoid broad rewrites unless the existing architecture makes a safe local correction impossible.

Never mark an issue fixed merely because code was changed.

PHASE 22: REGRESSION MATRIX

Every repair must trigger regression analysis.

Map:

Defect → Changed Components → Dependent Flows → Regression Tests → Result

Re-run all affected flows.

After significant changes, rerun foundational flows including:

- launch
- authentication
- session restoration
- dashboard
- core food logging
- data persistence
- navigation
- subscriptions where affected

A repair that breaks another flow is not complete.

PHASE 23: FINAL CLEAN-ROOM VALIDATION

After remediation, perform a final validation from a fresh-user perspective.

Do not rely on previous successful tests.

Re-test the production candidate as though this is the first time you have seen it.

Validate the complete Application Flow Map again, prioritizing critical paths.

Compare results against the original defect register.

Every P0, P1, and P2 finding must have a final status backed by evidence.

---

EVIDENCE STANDARD

Use this hierarchy:

Level A

Executed and observed directly.

Level B

Verified through automated tests or controlled simulation.

Level C

Strongly verified through code/configuration inspection.

Level D

Inference only.

Every major conclusion must state its evidence level.

Do not represent Level C or D evidence as real-device testing.

Screenshots alone do not prove backend correctness.

Code inspection alone does not prove runtime behavior.

A successful build does not prove production readiness.

---

ANTI-HALLUCINATION RULE

Never claim:

- "tested"
- "verified"
- "secure"
- "working"
- "production ready"
- "passed"

unless you possess evidence supporting the claim.

When testing is impossible because of missing credentials, hardware, sandbox restrictions, third-party access, Apple/Google configuration, or another limitation, report:

NOT VERIFIED

Explain precisely why.

Then provide the exact validation procedure required.

Unknown is an acceptable result.

Fabricated certainty is not.

If these conditions are not met, the verdict must be:

NO-GO FOR PRODUCTION

Do not soften the verdict.

FINAL OPERATING PRINCIPLE

The goal is not to make the repository look clean.

The goal is not to produce a long report.

The goal is not to confirm previous work.

The goal is to discover the truth about the application before customers discover it for us.

Assume hidden defects exist.

Search for them systematically.

Prove what works.

Expose what does not.

Fix confirmed defects carefully.

Retest everything affected.

Do not declare Calora production ready until the evidence supports that conclusion.

Begin with Phase 0: Protect the Project, then perform System Discovery and the Application Flow Map before broad execution.
