CALORA INTELLIGENCE — PHASE 2A.0

Progress Intelligence Real-Device Validation & Release Gate

Mission

Validate the existing Progress Contextual Intelligence card under realistic native-device conditions before authorizing any further visible Intelligence rollout.

This is a validation and hardening mission.

It is not permission to expand Contextual Intelligence.

The Progress overview is currently the only authorized visible Intelligence surface.

The existing architecture must remain:

Current authenticated account
        ↓
Account-isolated local state
        ↓
Intelligence Foundation
        ↓
Deterministic transient selector
        ↓
Delivery gate
        ↓
ONE eligible Progress insight

No persistent Intelligence storage.

No Intelligence API.

No Coach integration.

No Today Intelligence.

No post-log Intelligence.

No proactive Intelligence.

---

1. ABSOLUTE SCOPE RULE

Do not implement anything outside the explicit mission, even if you independently determine it would be safe, useful, or beneficial.

If you discover a desirable improvement outside this mission:

1. document it;
2. classify its importance;
3. recommend it in the final report;
4. DO NOT implement it.

Do not independently authorize additional Intelligence surfaces.

---

2. ESTABLISHED BASELINE

Preserve the Phase 1.9 architecture.

The existing selector:

- consumes Foundation facts only;
- is deterministic;
- returns at most one structured result;
- requires acceptable confidence;
- requires fresh facts;
- rejects incompatible source watermarks;
- performs no network request;
- performs no persistence;
- performs no logging of sensitive insight content.

The currently enabled visible flag is:

intelligence.insights.progress = ON

Keep these OFF:

intelligence.facts.server_adapter = OFF
intelligence.insights.today = OFF
intelligence.insights.post_log = OFF
intelligence.coach.fact_context = OFF
intelligence.feedback = OFF
intelligence.proactive = OFF

Do not change those states.

---

3. FIRST STEP — VERIFY IMPLEMENTATION BEFORE TESTING

Before device testing, inspect the actual Progress integration.

Confirm:

- where the card is mounted;
- which Foundation facts it receives;
- which delivery gate controls it;
- that no duplicate selector exists;
- that no raw state bypasses the Foundation;
- that the card cannot persist;
- that the card cannot trigger network activity;
- that no account-specific result is retained in React state or global context.

If the implementation differs materially from the Phase 1.9 report, stop and report the discrepancy.

5. TEST A — ELIGIBLE INSIGHT

Create or use safe representative local test data that should produce a valid high/medium-confidence Progress insight.

Verify:

- Progress opens normally;
- exactly one eligible insight appears;
- insight content corresponds to Foundation facts;
- title/message are understandable;
- no raw evidence identifiers appear;
- no account ID appears;
- no food-log ID appears;
- no internal diagnostic information appears;
- card layout works correctly.

Record the exact insight category generated.

---

6. TEST B — NO DATA

Test a new/empty account state.

Expected behavior:

No misleading contextual card.

Verify the selector does not invent a nutrition assessment.

Document whether the result is:

no_insight
insufficient_data

or another approved inactive state.

---

7. TEST C — LOW CONFIDENCE

Construct a valid low-confidence scenario.

Verify:

- no active Progress insight is displayed when the delivery rules prohibit it;
- the UI does not substitute a stronger claim;
- existing Progress content remains usable.

---

8. TEST D — STALE DATA

Construct or simulate stale Foundation facts.

Verify:

- stale insight is not displayed;
- old insight disappears rather than remaining visually cached;
- Progress itself remains functional.

---

9. TEST E — MIXED WATERMARKS

Provide facts with incompatible source watermarks.

Verify:

- no active insight is delivered;
- selector/delivery gate fails closed;
- no previously eligible card remains visible.

---

10. TEST F — LIVE RECOMPUTATION

Start with an eligible Progress insight.

Then change relevant Calora state through normal application behavior.

Examples:

- add food;
- edit food;
- delete food;
- change relevant target where supported.

Verify:

old facts
↓
state change
↓
new Foundation facts
↓
selector recomputes
↓
old insight disappears or changes

No stale insight may remain.

---

11. TEST G — ACCOUNT SWITCH

This is a critical release gate.

Scenario:

USER_A
→ eligible Progress insight visible

SIGN OUT

USER_B
→ different or empty state

Verify:

- USER_A insight disappears during scope reset;
- USER_A insight does not flash after USER_B becomes active;
- USER_B receives only USER_B-derived output;
- no USER_A title/message remains;
- no USER_A local state appears anywhere on Progress.

Then switch back to USER_A.

Verify USER_A insight is recomputed only after USER_A state hydrates.

---

12. TEST H — SIGN-OUT

While an insight is visible:

Sign out.

Verify:

- card disappears immediately with account scope reset;
- signed-out/onboarding state contains no previous insight;
- no previous nutrition information flashes during transition;
- no network request attempts to preserve the insight.

---

13. TEST I — APP RESTART

Test:

USER_A signed in
→ eligible insight
→ close app
→ restart

Verify:

- account-local state hydrates;
- insight is recomputed from current Foundation facts;
- the previous insight itself was not persisted;
- no card appears before hydration is safe.

Repeat where practical with USER_B.

---

14. TEST J — OFFLINE

Disable network connectivity after the authenticated local state is available.

Open Progress.

Verify:

- eligible transient insight can still compute locally;
- selector makes no network request;
- Progress does not become dependent on Intelligence network availability;
- existing offline Calora behavior remains intact.

Do not alter authentication behavior merely to manufacture an offline test.

---

15. TEST K — PERFORMANCE

Measure, where tooling allows:

- Progress render with flag OFF;
- Progress render with flag ON;
- Foundation snapshot generation;
- selector execution;
- delivery-gate evaluation.

Report actual measurements.

Distinguish:

NODE/VITEST
EMULATOR
SIMULATOR
PHYSICAL DEVICE

Do not convert development-machine measurements into claimed phone performance.

Look for:

- visible jank;
- delayed Progress rendering;
- unnecessary repeated computation;
- excessive re-renders;
- blocking work.

21. CONTENT QUALITY REVIEW

Review every currently supported Progress insight category.

Check for language that could be:

- judgmental;
- diagnostic;
- causal without evidence;
- medically prescriptive;
- falsely precise;
- misleading about incomplete logs.

Preserve factual language.

For example, distinguish:

No breakfast logged

from:

You skipped breakfast

Do not infer behavior that Calora did not observe.

Any wording correction must remain deterministic and within the existing selector scope.

25. PRODUCTION APPROVAL STANDARD

Do not recommend production publication of Progress Intelligence unless:

1. eligible data produces the correct insight;
2. insufficient data produces no misleading insight;
3. stale and low-confidence facts are suppressed;
4. account switching cannot leak previous-user output;
5. sign-out removes the card safely;
6. hydration cannot flash stale output;
7. selector remains network-free;
8. selector remains persistence-free;
9. Progress remains usable if Intelligence fails;
10. feature flag can disable delivery cleanly;
11. regressions remain green.

If native accessibility cannot be executed automatically, production approval may be conditional on manual VoiceOver/TalkBack validation.
