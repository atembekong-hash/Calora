CALORA INTELLIGENCE — PHASE 1.8A

Infrastructure Feasibility + Restricted Phase 2A Safety Gate

Mission

Perform a focused architecture investigation to answer two separate questions:

Question A: Can Calora's current managed PostgreSQL environment reliably support the proposed least-privilege runtime role + transaction-local identity + PostgreSQL RLS architecture across development, deployment, production, credential rotation, and rollback?

Question B: If full database-level RLS cannot yet be implemented, can a restricted early phase of Calora Contextual Intelligence safely begin using the already-built deterministic/read-only Intelligence Foundation and existing proven API authorization boundary, without introducing new persistent sensitive Intelligence data?

This is primarily an investigation and decision phase.

Do not force implementation merely to obtain a PASS.

---

PART I — CURRENT BASELINE

Treat these Phase 1.8 findings as established until direct evidence disproves them:

- Calora domain data lives in managed PostgreSQL.
- Supabase provides authentication.
- The API currently uses one "DATABASE_URL".
- The effective PostgreSQL runtime role is "postgres".
- That role is superuser, table owner, role creator, and bypasses RLS.
- Runtime and schema-management privileges are not separated.
- No dedicated "calora_api" runtime role currently exists.
- No transaction-local database user context exists.
- All 19 "calora_*" tables currently have RLS disabled.
- Existing API authorization remains the proven tenant-isolation boundary.
- Phase 1.8 intentionally made no database or application connection changes.

Do not repeat Phase 1.8 blindly.

Investigate the unresolved platform questions.

---

PART II — REPLIT POSTGRESQL CAPABILITY INVESTIGATION

Determine conclusively whether the managed PostgreSQL environment supports the target architecture.

Investigate actual platform behavior and available project/database controls, not assumptions.

Determine whether Calora can safely maintain:

1. a dedicated non-superuser runtime PostgreSQL role;
2. a separate credential for that role;
3. separate migration/admin credentials;
4. custom grants;
5. RLS policies;
6. helper functions required by RLS;
7. transaction-local settings;
8. safe "pg.Pool" behavior;
9. credential rotation;
10. production deployment;
11. persistence of custom roles/policies after publishing;
12. rollback.

Inspect available Replit project/database configuration, deployment mechanisms, documentation available to the environment, and existing repository lifecycle.

Do not expose credentials.

PART V — CONNECTION AND POOLING FEASIBILITY

Determine whether transaction-local identity is technically reliable with Calora's actual connection architecture.

Investigate:

- "pg.Pool";
- direct vs pooled upstream connection;
- transaction pooling if any;
- session pooling if any;
- connection reuse;
- "SET LOCAL";
- transaction boundaries;
- reconnect behavior;
- whether transaction-local custom settings survive only within the intended transaction.

The required property is:

USER_A context
exists only inside USER_A transaction

COMMIT / ROLLBACK

context disappears

USER_B receives no USER_A context

Do not implement the production transaction wrapper yet unless the entire lifecycle is proven safe.

PART VII — ROLLBACK FEASIBILITY

Design a concrete rollback procedure for a future least-privilege/RLS deployment.

Cover:

- bad runtime credentials;
- missing grants;

- broken transaction context;
- policy errors;
- failed deployment;
- custom role disappearance;
- connection failures.

The rollback procedure must restore service without losing data.

It must not require an uncontrolled permanent return to superuser runtime after the architecture has been declared secure.

Classify rollback:

DESIGNED BUT NOT TESTED
NOT AVAILABLE

PART X — DEFINE THREE INTELLIGENCE CLASSES

Classify future Intelligence capabilities into:

CLASS A — SAFE NOW

Requirements:

- reads existing data through existing authenticated API boundary;
- deterministic;
- no new sensitive persistent Intelligence records;
- no cross-user processing;
- no autonomous action;
- no LLM-generated facts treated as truth;
- no background profiling.

CLASS B — REQUIRES ADDITIONAL CONTROLS

Examples may include:

- persisted Intelligence history;
- server-side derived user profiles;
- longitudinal behavioral models;
- proactive background analysis;
- cross-session personalization;
- Coach memory derived from Intelligence;
- new sensitive derived records.

Identify the exact missing security control for each.

CLASS C — NOT APPROPRIATE YET

Examples may include:

- autonomous interventions;
- high-confidence health claims unsupported by data;
- opaque behavioral profiling;
- uncontrolled LLM-derived nutrition facts;
- cross-user/global learning using private data.

Classify based on the actual Calora architecture.

PART XII — PRIVACY AND SECURITY BOUNDARY

For restricted Phase 2A, prove that:

- every insight belongs only to the authenticated user;
- all underlying reads use existing server-resolved identity;
- no arbitrary "user_id" can be supplied;
- no insight response leaks another user's information;
- no Intelligence cache can cross users;
- no logs contain sensitive derived nutrition information unnecessarily;
- logout/account switching cannot expose the previous user's insight;
- account deletion does not leave new Intelligence records because Phase 2A creates none.

If any of these cannot be guaranteed, Phase 2A remains blocked.
