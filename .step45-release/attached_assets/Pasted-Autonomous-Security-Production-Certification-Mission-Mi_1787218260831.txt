Autonomous Security Production Certification Mission

Mission

MISSION: Perform a complete security audit, adversarial validation, remediation, and production-security certification of the entire application and every system it depends upon.

Treat the application as potentially insecure until evidence demonstrates otherwise.

Your responsibility is to discover the complete attack surface, identify exploitable weaknesses and unsafe assumptions, repair root causes, verify every repair, test for regressions, and determine whether the application is fit for production.

Operate only against the application's authorized codebase, accounts, infrastructure, test environments, and systems. Never perform destructive testing against real users, real financial transactions, or unauthorized third-party infrastructure.

Do not limit the audit to a predefined vulnerability checklist. Use the architecture and observed behavior of the actual application to discover additional attack paths.

---

1. Build the Complete Security Model

Before changing code, understand the system.

Map:

- Applications and clients
- Frontend and mobile code
- Backend services
- APIs and endpoints
- Databases
- Storage
- Authentication systems
- Authorization systems
- User roles
- Administrative capabilities
- Payments and entitlements
- AI and model integrations
- File handling
- Background workers
- Queues and scheduled jobs
- Webhooks
- Push notifications
- Email systems
- Analytics
- Logging and monitoring
- Third-party SDKs
- External APIs
- Cloud services
- Deployment infrastructure
- CI/CD
- Environment configuration
- Secrets
- Dependencies
- Build and release pipeline
- Network boundaries
- Publicly reachable services
- Sensitive data flows

Identify every trust boundary and every point where untrusted data enters the system.

Identify what each security boundary protects and what would happen if that boundary failed.

Create a Security Surface Map and use it as the audit plan.

---

2. Threat Model the Application

For every important system, determine:

- What assets require protection?
- Who can access them?
- Who should never access them?
- What does the system trust?
- Can that trust be manipulated?
- What happens if the client lies?
- What happens if requests are modified?
- What happens if identifiers are changed?
- What happens if requests are replayed?
- What happens if operations occur out of order?
- What happens if two operations occur simultaneously?
- What happens if an authenticated user becomes malicious?
- What happens if one account attempts to access another account?
- What happens if a low-privilege user attempts privileged operations?
- What happens if an integration is compromised or unavailable?

Prioritize testing according to likelihood, exploitability, and impact.

---

3. Authentication and Session Security

Audit every authentication mechanism.

Test applicable scenarios involving:

- Registration
- Login
- Logout
- Email verification
- OTP
- Password reset
- Account recovery
- Social authentication
- Token creation
- Token validation
- Token refresh
- Token expiration
- Token revocation
- Session persistence
- Concurrent sessions
- Cross-device sessions
- Remember-me behavior
- Reauthentication
- Deleted accounts
- Disabled accounts
- Expired accounts

Attempt to identify:

- Authentication bypass
- Account enumeration
- Weak recovery mechanisms
- OTP abuse
- Replay
- Session fixation
- Stale sessions
- Improper logout
- Weak token validation
- Missing expiration enforcement
- Client-side authentication trust
- Improper session invalidation
- Brute-force exposure
- Missing or ineffective rate limiting

Authentication success alone is insufficient. Verify the entire session lifecycle.

---

4. Authorization and Account Isolation

Treat authorization as a separate security boundary from authentication.

Enumerate protected resources and privileged operations.

For each one, test access as:

Unauthenticated user → legitimate owner → different authenticated user → lower-privilege user → elevated user

Attempt unauthorized access to applicable:

- Profiles
- Accounts
- Classes
- Student information
- Teacher information
- Files
- Messages
- History
- AI conversations
- Purchases
- Subscription state
- Premium functionality
- Settings
- Private records
- Administrative functionality
- Internal APIs

Test both read and write operations.

Changing a route, request, object identifier, account identifier, client state, or UI state must never grant authority that the backend has not independently verified.

Verify authorization at the authoritative server boundary.

7. Business Logic and Abuse Testing

Do not restrict the audit to technical vulnerabilities.

Attempt to misuse legitimate functionality in unintended ways.

Test applicable scenarios involving:

- Skipping required steps
- Reordering workflows
- Repeating one-time actions
- Replaying operations
- Manipulating client state
- Changing identifiers
- Bypassing limits
- Bypassing feature restrictions
- Circumventing premium requirements
- Creating inconsistent account states
- Exploiting race conditions
- Duplicate submissions
- Unauthorized role changes
- Abusing invitations or classroom membership
- Manipulating rewards, quotas, credits, or usage limits
- Exploiting cancellation or restoration logic

Assume attackers understand the product's business rules.

- Server-side purchase verification
- Receipt validation
- Subscription validation
- Entitlement integrity
- Restore-purchase security
- Cancellation handling

9. Data Security and Privacy

Identify and classify sensitive data.

Trace it through:

Collection → Transmission → Processing → Storage → Retrieval → Logging → Backup → Deletion

Verify:

- Minimum necessary collection
- Appropriate access controls
- Secure transport
- Secure storage
- Account isolation
- Appropriate retention
- Safe deletion
- Safe logging
- Safe analytics
- Safe backups
- No unintended disclosure
- No sensitive information in URLs where inappropriate
- No secrets in client-visible code
- No sensitive information in error messages

Test whether one user can obtain another user's information through any available interface.

10. Secrets and Credential Security

21. Automated Security Analysis

---

22. Repair Protocol

For every confirmed security defect:

1. Reproduce it safely.
2. Determine the root cause.
3. Determine the affected trust boundary.
4. Assess severity and realistic impact.
5. Search for the same weakness elsewhere.
6. Implement the strongest maintainable repair.
7. Verify the exploit path no longer succeeds.
8. Verify legitimate behavior still succeeds.
9. Regression-test affected systems.
10. Retest related attack paths.
11. Record objective evidence.

Do not merely hide vulnerable UI.

Do not suppress errors instead of repairing their cause.

Do not weaken another security control to make a test pass.

---

23. Security Validation Ledger

Maintain a live Security Validation Ledger throughout the mission.

For every security surface record:

- Surface
- Asset protected
- Trust boundary
- Threat tested
- Severity
- Expected behavior
- Actual behavior
- Vulnerability found
- Root cause
- Repair
- Exploit retest
- Functional regression result
- Evidence
- Residual risk

Use:

NOT TESTED → IN PROGRESS → VULNERABLE → REPAIRING → RETESTING → PASSED

Never mark PASSED because code looks correct.

PASSED requires objective validation evidence.

---

24. Final Adversarial Regression Sweep

After individual security surfaces have passed, perform a fresh application-wide adversarial sweep.

Approach the application as if you had not participated in the repairs.

Focus especially on combinations of individually safe behaviors that may become unsafe when chained together.

Revalidate:

- Authentication
- Authorization
- Account isolation
- Role boundaries
- APIs
- Sessions
- Sensitive data
- Payments
- Entitlements
- AI
- Files
- Integrations
- Secrets
- Dependencies
- Production configuration
- Business logic

Attempt to identify attack paths missed during the first audit.

If a new weakness is discovered, reopen the affected security surface, repair it, recertify it, and repeat the relevant regression testing.

---

Strict Production Security Gate

Do not certify production security merely because:

- The application builds.
- Automated tests pass.
- A vulnerability scanner reports no findings.
- Authentication works.
- HTTPS is enabled.
- Secrets were removed.
- Dependencies were updated.
- Previously discovered vulnerabilities were repaired.

Production-security readiness requires evidence across the complete mapped attack surface.

The mission may conclude only when:

- The Security Surface Map is complete to the extent reasonably discoverable.
- Every critical security boundary has been tested.
- Every applicable high-risk attack path has been exercised safely.
- No known unresolved critical or high-severity exploitable vulnerability remains.
- Security repairs have been independently retested.
- Legitimate user workflows still function after security repairs.
- Relevant regression testing has passed.
- Production configuration has been reviewed where accessible.
- Untested surfaces and external limitations are explicitly identified.
- Residual security risk is documented honestly.

Never claim the application is "unhackable," "100% secure," or permanently vulnerability-free.

Certify only what the evidence supports.
