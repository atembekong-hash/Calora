8. USER IDENTITY MODEL

The internal CaloraApp identity must remain distinct from the external authentication-provider identity.

Use:

"calora_users.id"

as the authoritative internal CaloraApp user ID.

Use:

"calora_users.externalId"

to store the Supabase Auth user ID.

The target relationship is:

Supabase Auth user.id

↓

"calora_users.externalId"

↓

"calora_users.id"

↓

all user-owned CaloraApp records.

Do NOT casually replace every internal "userId" foreign key with the Supabase Auth UUID.

The separation between provider identity and application identity is deliberate and should be preserved.

---

9. WHY THIS IDENTITY SEPARATION MATTERS

Keeping an internal CaloraApp user ID provides:

- reduced vendor coupling
- cleaner migrations later
- safer provider changes
- stable database ownership
- better account-linking flexibility
- support for multiple external providers
- future enterprise/admin options
- cleaner RevenueCat identity decisions

Supabase should authenticate the user.

CaloraApp should own the application-level identity.

---

10. STABLE USER RECORD CREATION

After successful Supabase authentication:

1. Obtain the authenticated Supabase user ID.
2. Look up:

"calora_users.externalId"

3. If a matching user exists, load the existing CaloraApp user.
4. If not, create a new "calora_users" record.
5. Store the Supabase user ID in "externalId".
6. Return the internal CaloraApp user ID to the authenticated application layer.

This operation must be race-safe and idempotent.

Multiple requests must not create duplicate users.
