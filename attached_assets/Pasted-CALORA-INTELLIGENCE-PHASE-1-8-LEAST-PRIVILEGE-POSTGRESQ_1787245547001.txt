CALORA INTELLIGENCE — PHASE 1.8 LEAST-PRIVILEGE POSTGRESQL + RLS ARCHITECTURE

Mission

Proceed with Phase 1.8: Least-Privilege PostgreSQL + RLS Architecture.

The purpose of this phase is to move Calora away from the current shared PostgreSQL superuser runtime model and establish a real, testable database-level tenant-isolation layer behind the existing API authorization layer.

The target architecture is:

Supabase Auth
      ↓
Calora API verifies bearer token
      ↓
Resolve trusted internal Calora user UUID
      ↓
Begin DB transaction
      ↓
Set transaction-local trusted user context
      ↓
Execute queries through non-superuser API role
      ↓
PostgreSQL RLS enforces ownership
      ↓
Commit / rollback
      ↓
Request identity disappears

This phase must preserve the existing API ownership predicates. RLS is defense in depth, not a replacement for application authorization.

---

2. PHASE 1.7 BASELINE

Preserve the established facts:

- Supabase is authentication only.
- Calora domain data lives in managed PostgreSQL.
- API authorization currently derives trusted identity from Supabase.
- The API currently connects as PostgreSQL "postgres".
- "postgres" is superuser, table owner, and bypasses RLS.
- No request-specific database identity exists.
- Existing API tenant isolation tests pass.
- Existing child-ownership hardening must remain.

Do not regress any of this.

---

3. OBJECTIVE A — SEPARATE SCHEMA ADMINISTRATION FROM API RUNTIME

Create a clean privilege boundary between:

Schema/admin role

Responsible for:

- schema application;
- DDL;
- migrations;
- functions/triggers;
- RLS policy installation;
- grants;
- operational provisioning.

API runtime role

Responsible only for:

- required DML;
- required function execution;
- normal application queries.

The API runtime role must not be:

- superuser;
- database owner;
- table owner;
- "BYPASSRLS";
- capable of arbitrary schema modification;
- capable of assuming unsafe privileged roles.

Do not remove the managed platform's schema/admin capability if it is required for deployment.

Instead, keep elevated privileges out of the normal request path.

---

4. OBJECTIVE B — CREATE OR PROVISION A LEAST-PRIVILEGE API ROLE

Determine the safest managed mechanism for a dedicated Calora runtime role.

Conceptual name:

"calora_api"

or repository-appropriate equivalent.

Before creation, verify:

- role lifecycle;
- how credentials are stored;
- whether Replit-managed deployment can preserve it;
- whether production propagation is supported;
- how password/credential rotation works;
- whether the platform may overwrite custom roles.

The role should receive only required privileges.

Audit every grant explicitly.

---

5. OBJECTIVE C — REQUEST-SCOPED DATABASE IDENTITY

Implement a transaction-local user-context contract.

The identity must come from:

verified Supabase user
→ server-side Calora user mapping
→ internal Calora UUID

Never from request JSON.

Use a PostgreSQL transaction-local mechanism such as a custom setting only if compatible with the platform.

Conceptual example:

SET LOCAL app.current_user_id = '<trusted internal uuid>';

Do not copy this syntax blindly if the repository/platform needs another safe mechanism.

Requirements:

- transaction-local;
- cleared automatically after commit/rollback;
- impossible for a normal client request to set directly;
- safe with "pg.Pool";
- safe if the upstream platform uses pooling;
- never leak USER_A context into USER_B queries.

---

6. OBJECTIVE D — TRANSACTION CONTRACT

Determine how current user-scoped queries must run under the new security model.

If RLS depends on transaction-local identity, user-owned database operations must execute inside a transaction that establishes the trusted context first.

Create a reusable server-side helper, conceptually:

withAuthenticatedDbUser(...)

or equivalent.

It should:

1. receive only a server-verified internal Calora UUID;
2. acquire a pooled connection;
3. begin a transaction;
4. set transaction-local identity;
5. execute callback/query work;
6. commit on success;
7. rollback on failure;
8. release connection safely.

Do not permit arbitrary caller-defined SQL identity.

---

7. OBJECTIVE E — RLS DESIGN BY TABLE CLASS

Do not apply identical policies to all 19 tables.

Use the Phase 1.7 classification.

USER-OWNED

Examples:

- profiles
- diary
- weights
- saved meals
- recipes
- sync mutations
- consent

Policy should enforce the row's internal owner against the transaction-local verified Calora user.

USER-OWNED CHILD

Examples:

- recipe items
- capture candidates

Ownership must traverse the parent.

SHARED

Examples:

- food items
- recipe nutrition

Do not apply private ownership semantics.

Decide explicit read/write access.

SERVICE-ONLY / SYSTEM

Examples:

- subscriptions where server-managed
- capture rate limits
- deletion states
- referral qualification/redemption where applicable

Normal user-scoped API role should not receive arbitrary direct access.

TWO-PARTY

Referral records require special logic.

Do not shoehorn them into simple one-owner RLS.

---

8. OBJECTIVE F — RLS POLICIES

Where appropriate, implement policies for:

- SELECT
- INSERT
- UPDATE
- DELETE

Use both:

- "USING"
- "WITH CHECK"

where needed.

Policies must be source-controlled.

Do not trust a submitted "user_id".

For INSERT/UPDATE, the policy must prevent a valid USER_A request from creating or reassigning a row to USER_B.

---

9. OBJECTIVE G — KEEP API AUTHORIZATION

Do not remove existing API predicates.

The target is:

API authorization
+
database authorization

not one or the other.

For current active routes:

- diary
- sync
- capture child flow
- deletion
- referral

preserve the existing server-side ownership checks.

RLS should catch future mistakes, not make developers stop scoping queries correctly.

---

10. OBJECTIVE H — ADMIN / SERVICE BYPASS DESIGN

Some operations legitimately need cross-user access.

Examples:

- account deletion;
- deletion recovery;
- operational cleanup;
- referral settlement;
- future administrative jobs.

Design a deliberate elevated execution path.

Requirements:

- ordinary API requests cannot invoke it arbitrarily;
- elevated path uses a separate role or explicit trusted context;
- no user-controlled identifier is accepted as authorization;
- elevated access is logged safely;
- service role must not become the default runtime connection.

Do not give "calora_api" "BYPASSRLS".

---

11. OBJECTIVE I — ACCOUNT DELETION COMPATIBILITY

RLS must not break account deletion.

Test:

1. authenticated deletion request;
2. deletion state/fence;
3. privileged worker behavior;
4. deletion of direct user-owned rows;
5. cascade to child records;
6. referral anonymization behavior;
7. operational records;
8. Supabase Auth deletion;
9. retry and recovery;
10. idempotency.

Use disposable non-production identities.

---

12. OBJECTIVE J — REAL SUPABASE USER_A / USER_B TEST

Phase 1.7 used real PostgreSQL data but mocked the Supabase verifier boundary.

This phase should close that gap if safe.

Create two disposable Supabase Auth accounts:

"USER_A"

"USER_B"

Use real Supabase sessions/tokens.

Run requests through the real Calora API auth path.

Then prove:

USER_A cannot access USER_B data.

USER_B cannot access USER_A data.

Test both API and database-level enforcement.

Delete the disposable test users afterward.

Do not use real customer accounts.

---

13. OBJECTIVE K — DIRECT DATABASE RLS TEST

Using the effective non-superuser API role:

Establish USER_A transaction-local context.

Verify:

- USER_A can SELECT own rows;
- USER_A cannot SELECT USER_B rows;
- USER_A cannot UPDATE USER_B rows;
- USER_A cannot DELETE USER_B rows;
- USER_A cannot INSERT a row owned by USER_B.

Repeat for child ownership.

Then establish USER_B context and repeat.

This must be a genuine DB-level test, not merely an API response test.

---

14. OBJECTIVE L — CONNECTION-LEAK TEST

This is critical.

Test pooled connection identity isolation.

Example adversarial sequence:

Request 1:
USER_A
→ transaction
→ set local A
→ query
→ commit

Same physical pooled connection reused

Request 2:
USER_B
→ transaction
→ set local B
→ query

Verify USER_B cannot inherit USER_A identity.

Also test:

- rollback;
- thrown exception;
- timeout;
- early return;
- connection release;
- retry.

No request context may survive transaction completion.

---

15. OBJECTIVE M — FAILURE MODE TESTING

Test:

- missing user context;
- malformed user context;
- unauthenticated request;
- invalid Supabase token;
- missing internal user mapping;
- transaction failure;
- DB reconnect;
- connection-pool exhaustion where practical;
- RLS policy error;
- admin operation under normal user role.

Fail closed for user-owned data.

16. OBJECTIVE N — ROLE/GRANT HARDENING

- create/drop arbitrary tables;
- alter policies;
- disable RLS;
- assume "postgres";
- grant itself privileges;
- read system/service-only data outside defined paths;
- execute dangerous functions;
- bypass RLS.

Document every privilege retained.

21. ROLLBACK REQUIREMENT

Before implementing security changes, define rollback.

Rollback must be able to restore a functioning API if:

- role credentials fail;
- grants are incomplete;
- RLS blocks legitimate operations;
- managed deployment does not preserve roles;
- transaction wrapper causes regression.

Do not leave Calora unable to access its database.

Do not solve rollback by permanently returning to superuser after declaring the new architecture secure.
