You are now executing CALORA IMAGE REMEDIATION MISSION 01.

PRIMARY OBJECTIVE

Fix Calora’s image system so that every food or meal image shown to a user is tied as closely as possible to the exact entity it represents.

A photo must not be reused for unrelated meals merely because they share a category.

Do not create artificial “uniqueness” by assigning random different food photos. Accuracy matters more than visual variety.

If an exact image cannot be verified, use a clearly identified representative image or neutral fallback rather than pretending that the image is exact.

SOURCE OF TRUTH

Use the existing project report:

IMAGE_AUDIT_01_COMPLETE_PROJECT_IMAGE_FORENSIC_REPORT.md

Treat that report as the baseline forensic evidence for this remediation.

Do not repeat the audit from scratch unless necessary to verify a change.

IMPORTANT CURRENT FINDINGS

The audit established:

- 57 runtime bundled image files exist.
- All 57 bundled files have unique SHA-256 hashes.
- 26 Planner meals have canonical image identities.
- 20 verified foods have canonical image identities.
- The major repetition problem is logical image reuse rather than duplicate image files.
- Restaurant foods currently collapse into only 11 representative image categories.
- FatSecret restaurant normalization currently does not preserve item-level images.
- Planner detail can bypass the stronger canonical identity path.
- FoodLogThumbnail can prioritize local representative imagery over a more specific valid remote image.
- Scan candidate image identity is not strongly bound to the verified candidate.
- Component-level capture images can be lost when accepted into the diary.
- Profile and Scan image surfaces lack sufficiently resilient image failure handling.
- Recipe imagery is comparatively strong but still needs provenance and cross-page deduplication improvements.
- Some screens correctly do not need imagery. Do not add decorative images everywhere.

MISSION RULE

For every consumer-facing food image, classify the image as one of:

1. EXACT VERIFIED IMAGE
   The image is tied to the exact meal, recipe, food, product, restaurant item, barcode product, or user-created entity.

2. REPRESENTATIVE IMAGE
   The image represents a category or role but is not guaranteed to depict the exact item.

3. FALLBACK
   Used only when no reliable image exists.

The application must never silently present category-level or fallback imagery as an exact item photograph.

Document the decision.

PHASE 4: RESTAURANT IMAGE ARCHITECTURE
==================================================

This is the largest product-integrity gap.

Current behavior maps many distinct restaurant menu items into approximately 11 representative categories.

Do NOT simply generate or manually assign random restaurant photos.

First investigate whether the currently configured provider or another already-integrated trusted source exposes an item-specific image field that Calora is currently discarding.

Check:

- raw FatSecret restaurant responses
- provider adapters
- normalized API schemas
- restaurant search response contracts
- client models
- persistence
- any existing provider image fields not currently surfaced

If an item-specific provider image exists:

- preserve it through normalization
- validate its host
- attach provider/source provenance
- pass it through API contracts
- use it as the exact image
- preserve fallback behavior when unavailable

If FatSecret truly provides no usable item-level photograph for this path, DO NOT fabricate exactness.

Keep the representative system as fallback.

Maintain visible wording equivalent to:

“Representative image · exact menu photography unavailable”

The wording may be adapted to existing UI style, but the meaning must remain clear.

Never infer an exact restaurant photograph from:

- brand name alone
- category
- food name keyword search
- visually similar menu item
- unrelated public image

If a future trusted item-level image source requires licensing, credentials, or a paid API not currently available, document it as a blocker rather than inventing a workaround.
