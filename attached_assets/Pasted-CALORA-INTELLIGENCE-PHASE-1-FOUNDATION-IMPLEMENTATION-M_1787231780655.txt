CALORA INTELLIGENCE — PHASE 1 FOUNDATION IMPLEMENTATION

Mission

Proceed with Phase 1 of the Calora Intelligence architecture based on the completed Phase 0 forensic audit.

This phase is foundational only.

The purpose is to create a deterministic, evidence-aware, versioned Intelligence Facts layer that can later support contextual insights, Progress interpretation, Planner intelligence, Recipes intelligence, and Calora Coach.

Do not implement the visible Intelligence experience yet.

Do not redesign Calora.

Do not rewrite Coach.

Do not introduce predictive or prescriptive AI behavior.

The objective is to establish one trusted facts layer beneath the existing product.

---

1. PHASE 1 CORE PRINCIPLE

The Intelligence system must not become a second source of nutrition truth.

Existing Calora state remains authoritative for:

- diary entries
- food logs
- user profile
- goals
- planner
- shopping
- recipes
- weight
- wellness
- activity
- local persistence

The Intelligence Foundation is read-only.

It consumes existing state and derives structured facts from it.

Architecture:

Existing Calora State
        ↓
Context Adapters
        ↓
Deterministic Facts
        ↓
Evidence / Provenance
        ↓
Confidence / Freshness
        ↓
Lifecycle / Invalidation
        ↓
Future Insights / Coach / UI

No LLM should be required for this pipeline.

4. STEP 2 — BUILD THE DETERMINISTIC FACTS ENGINE

Extract or wrap existing calculation logic rather than creating a competing implementation.

Reuse existing arithmetic from:

- Food Memory
- Today
- Progress
- weeklySignals
- livingState
- other relevant deterministic helpers

The purpose is to converge calculations.

The Facts Engine should initially support only high-confidence deterministic facts.

Examples:

Daily nutrition facts

- calories consumed
- calorie target
- calories remaining
- protein consumed
- protein target
- protein remaining
- carbohydrates consumed
- carbohydrate target
- fat consumed
- fat target

Where available and reliable:

- fiber
- sodium
- sugar
- additional nutrients already supported by Calora

---

Meal distribution facts

Examples:

breakfast calories
lunch calories
dinner calories
snack calories
percentage of daily calories by meal

---

Logging completeness facts

Examples:

number of meals logged
days sufficiently logged
days partially logged
days with no logs

Do not infer “the user skipped breakfast” solely because breakfast was not logged.

Distinguish:

not logged
logged zero
unknown

where appropriate.

---

Evidence partitions

Daily totals should be able to report what portion came from:

verified/provider data
manual/user-entered data
user-corrected data
AI-estimated data
recipe-estimated data
unknown provenance

Do not necessarily change existing user-visible totals.

This partition is for Intelligence evidence quality.

---

5. CALCULATION VERSIONING

Every deterministic fact must include a calculation schema/version.

Example:

calculationVersion: "nutrition-facts-v1"

Do not hard-code the version independently in many locations.

Create one shared source.

If future calculation rules change, old facts must remain identifiable by version.

---

6. SOURCE WATERMARK

Facts must be tied to the state from which they were calculated.

Create a lightweight deterministic source watermark or fingerprint.

It should change when relevant inputs change.

Examples:

- food added
- food deleted
- food modified
- goal modified
- target modified
- weight modified
- timezone changed

Avoid expensive full-history hashing on every render if a cheaper reliable strategy exists.

Document the chosen strategy.

---

7. FRESHNESS MODEL

Each fact must carry freshness state.

Suggested categories:

fresh
stale
expired
unknown

Freshness should not be determined by AI.

It should be derived from deterministic source state, timestamps, and invalidation rules.

---

8. MISSING-DATA MODEL

Missing data must be treated as a first-class state.

Examples:

missing_target
incomplete_day
missing_weight
missing_macros
unknown_provenance
insufficient_history

Do not convert absent data into zero unless the domain explicitly means zero.

This distinction is essential for future Intelligence.

---

9. EVIDENCE QUALITY MODEL

Implement deterministic evidence classification.

At minimum distinguish:

Stronger evidence

- nutrition label
- barcode/provider value
- structured known food
- explicit user correction

Moderate evidence

- user-entered value
- manually assembled food

Estimated evidence

- AI capture
- AI recipe nutrition
- other generated estimates

Unknown evidence

- legacy or unclassified entries

Do not automatically rank all providers above user corrections.

Document the exact ordering and reasoning.

The system must retain provenance rather than reducing everything to one confidence number.

---

10. CONFIDENCE FRAMEWORK

Build confidence from observable conditions.

Factors may include:

- evidence quality
- data completeness
- sample size
- consistency
- freshness
- proportion of estimated inputs
- conflicting values

Initial Phase 1 confidence must remain simple and explainable.

Avoid opaque scoring.

Example:

HIGH
MEDIUM
LOW
INSUFFICIENT

If numeric scores are used internally, map them clearly to the user-facing categories.

---

11. WEIGHT BASELINE UNIFICATION

The audit found potential disagreement between Coach and Progress weight baselines.

Create one shared deterministic selector for weight baseline and trend calculations.

Do not redesign Progress.

Do not change existing visible behavior unless tests prove the existing logic is inconsistent or incorrect.

First create the shared helper and parity tests.

If current systems disagree, report:

CURRENT PROGRESS RESULT
CURRENT COACH RESULT
PROPOSED CANONICAL RESULT
WHY THEY DIFFER

Do not silently choose one.

14. INVALIDATION ENGINE

Build deterministic invalidation.

Facts must be invalidated or recomputed when relevant state changes.

Cover at minimum:

- food added
- food edited
- food deleted
- target changed
- goal changed
- weight changed
- timezone changed
- day boundary changes
- preference changes that affect facts
- planner changes where relevant

Do not leave stale facts active.

Create unit tests for every invalidation path.

---

15. PERFORMANCE REQUIREMENTS

Do not recompute long periods of history on every React render.

Use:

- memoized pure functions
- selectors
- stable input fingerprints
- incremental calculation where useful
- bounded history windows
- lazy computation

Do not optimize blindly.

Measure.

Track calculation duration in development/test observability.

Today and logging must remain fast.

---

16. DO NOT PERSIST EVERYTHING YET

Do not begin by creating server tables for every Intelligence fact.

Phase 1 should first prove the model locally and deterministically.

Before adding persistent Intelligence tables, verify:

1. migration authority
2. Drizzle/startup DDL parity
3. production RLS
4. deletion behavior
5. retention behavior
6. tenancy guarantees

If these cannot be confirmed from the repository, document them as blockers.

Do not guess.

22. TESTING GATE 2 — PROVENANCE

Verify that:

- provider data remains provider data;
- manual data remains manual data;
- corrected values remain corrected;
- AI estimates remain estimated;
- recipe estimates remain estimated;
- unknown legacy data remains unknown.

A generated estimate must never become “verified” through aggregation.

---

23. TESTING GATE 3 — INVALIDATION

Test:

log food
→ facts update

edit food
→ previous facts invalidated
→ new facts calculated

delete food
→ stale facts disappear

change target
→ target comparison changes

change weight
→ weight fact changes

change timezone
→ day assignments recalculated correctly

No stale result may remain active.

---

24. TESTING GATE 4 — LOCAL-FIRST RESILIENCE

With API unavailable:

- food logging must work;
- Today must render;
- deterministic facts must still compute;
- no Intelligence error may block navigation;
- no infinite retry loop;
- no user-visible regression.

The Intelligence Foundation must degrade to silence rather than breaking Calora.

---

25. TESTING GATE 5 — PERFORMANCE

- meal log completion
- food edit
- food deletion
- Progress opening
- app hydration

STOP.

Do not force migration to the new result.

Investigate the discrepancy.

Classify it as:

existing logic bug
new facts bug
ambiguous product rule
missing data
provenance mismatch
timezone/day-boundary mismatch

Return the evidence.

Wait for approval.

---

28. SUCCESS STANDARD

Phase 1 succeeds when Calora has one deterministic Intelligence Foundation capable of answering:

- What do we actually know?
- Where did the data come from?
- How complete is it?
- How fresh is it?
- How confident are we?
- Which calculation version produced it?
- What changed since the last calculation?
- When should this fact stop being trusted?

All of this must happen without changing the visible Calora experience.
