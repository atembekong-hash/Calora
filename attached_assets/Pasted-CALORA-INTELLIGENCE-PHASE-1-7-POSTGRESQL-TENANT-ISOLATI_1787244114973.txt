CALORA INTELLIGENCE — PHASE 1.7 POSTGRESQL TENANT-ISOLATION HARDENING

Mission

Proceed with Phase 1.7: PostgreSQL Tenant-Isolation Hardening for Calora.

The previous Supabase security work established that:

- Supabase is the active Calora authentication provider;
- the Calora application tables do not live in Supabase;
- the real Calora domain data lives in the separate managed PostgreSQL database;
- Phase 2 remains blocked until tenant isolation is proven in the database that actually stores Calora user data.

This phase must therefore inspect, harden, validate, and document the actual PostgreSQL authorization and tenant-isolation model used by Calora.

This is not a UI task.

This is not Phase 2.

Do not enable visible Intelligence.

Do not enable server-persisted Intelligence facts yet.

---

1. CORE SECURITY QUESTION

Establish the exact authorization chain:

Supabase authenticated user
        ↓
Supabase user identity
        ↓
Calora API bearer verification
        ↓
Calora internal user mapping
        ↓
internal user_id
        ↓
PostgreSQL queries
        ↓
user-owned Calora records

Document every trust boundary.

Do not assume the chain is secure merely because the API currently filters by "user_id".

Prove it.

3. OBJECTIVE A — MAP AUTH TO DATABASE IDENTITY

Inspect the actual repository and database path.

Determine:

1. how Supabase bearer tokens are verified;
2. which Supabase identity field is trusted;
3. how that external identity maps to "calora_users";
4. how the internal Calora UUID is derived;
5. whether the mapping can be forged;
6. whether every user-specific API route uses the verified internal identity;
7. whether any route trusts "user_id" from request body/query/path;
8. whether any helper can query user-owned rows without passing verified identity;
9. whether service/admin routes bypass normal ownership checks;
10. whether background jobs operate across users and how they are constrained.

Produce a trust-boundary diagram.

---

4. OBJECTIVE B — DATABASE CONNECTION MODEL

Inspect how the API connects to PostgreSQL.

Determine:

- connection pool/library;
- database role used;
- whether every API request uses the same DB role;
- whether per-user DB roles exist;
- whether PostgreSQL session variables are set;
- whether transaction-local identity is available;
- whether PgBouncer or another pooler is involved;
- whether prepared statements or transaction pooling would affect session-based security;
- whether database credentials are server-only;
- whether any client has direct PostgreSQL access.

This determines whether PostgreSQL RLS can work correctly.

---

5. OBJECTIVE C — DETERMINE WHETHER RLS IS APPROPRIATE

Do not assume RLS is automatically the right answer.

Evaluate at least these models:

Model A — API-only authorization

All user isolation enforced in application queries.

Model B — PostgreSQL RLS using a request-scoped user context

Example conceptual model:

API verifies Supabase token
→ resolves internal user ID
→ starts transaction
→ sets transaction-local user context
→ PostgreSQL RLS checks that context

Model C — Separate database roles

Evaluate only if architecture supports it.

Model D — Hybrid

API ownership checks plus database-enforced RLS or views.

Compare:

- correctness;
- security strength;
- compatibility with current pooling;
- performance;
- operational complexity;
- failure modes;
- testability;
- risk of accidental cross-user access.

Recommend one model.

Do not implement RLS until the connection model proves it safe.

10. OBJECTIVE H — REAL CROSS-USER ADVERSARIAL TESTS

Create or use two dedicated non-production identities:

USER_A
USER_B

Use normal Supabase-authenticated sessions.

Create representative records for both users.

Then verify USER_A cannot read, modify, or delete USER_B resources.

Test at minimum:

- profile;
- diary;
- weights;
- saved meals;
- recipes;
- recipe items;
- capture sessions;

- delete by guessed ID;
- bulk/sync mutation;

Do not claim tenant isolation without executed negative tests.

11. OBJECTIVE I — DIRECT DATABASE ADVERSARIAL TEST

If PostgreSQL RLS or another DB-level mechanism is implemented, test it directly.

Verify that the effective application database role cannot access another user's rows when the transaction user context is USER_A.

Test SELECT, INSERT, UPDATE, DELETE.

If the application DB role necessarily remains fully privileged and database isolation cannot be meaningfully enforced, report:

DATABASE-LEVEL TENANT ISOLATION: NOT ENFORCEABLE WITH CURRENT CONNECTION MODEL

Then describe the strongest safe architecture available.

Do not pretend API filtering equals DB isolation.

---

12. OBJECTIVE J — SAFE RLS IMPLEMENTATION, ONLY IF APPROPRIATE

If and only if the investigation proves PostgreSQL RLS is compatible with the current connection/pooling model:

1. design request-scoped identity propagation;
2. use transaction-local state rather than unsafe global session state where appropriate;
3. prevent identity leakage between pooled connections;
4. define RLS policies for user-owned tables;
5. define transitive policies for child tables;
6. keep shared tables intentionally shared;
7. keep operational tables inaccessible to user context;
8. ensure admin/service operations use a deliberate bypass path;
9. source-control all policy definitions;
10. test rollback.

Do not rely on client-supplied user IDs to populate the DB identity context.

The API must derive the database identity from the verified Supabase token.

---

13. OBJECTIVE K — SERVICE / ADMIN ACCESS

Audit every path that needs cross-user access.

Examples:

- account deletion;
- RevenueCat reconciliation;
- referrals;
- support/admin operations;
- cleanup;
- scheduled jobs;
- sync recovery.

For each:

- document why it needs elevated access;
- enforce explicit service context;
- prevent ordinary user calls from reaching it;
- validate auditability;
- ensure the elevated path cannot be triggered by forged user identifiers.

14. OBJECTIVE L — ACCOUNT DELETION END-TO-END

Test account deletion against the real managed PostgreSQL database.

Verify:

- write fence starts;
- new user writes are rejected;
- user-owned records are removed or transitioned as designed;
- child rows are handled;
- retries are safe;
- deletion is idempotent;
- Supabase Auth deletion remains coordinated;
- no orphaned private rows remain;
- no future Intelligence records can escape deletion once persistence exists.

Use dedicated non-production accounts only.

Do not delete real user accounts.
