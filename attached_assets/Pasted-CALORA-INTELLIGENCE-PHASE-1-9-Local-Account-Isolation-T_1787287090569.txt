CALORA INTELLIGENCE — PHASE 1.9

Local Account Isolation + Transient Insight Engine

Mission

Proceed with Phase 1.9: Local Account Isolation + Transient Insight Engine.

This phase has two goals:

1. make Calora’s local state safe across sign-out, account switching, and shared-device use;
2. build a pure, deterministic, transient contextual-insight selector over the existing Intelligence Foundation.

Do not enable visible Contextual Intelligence yet.

Do not add persistent Intelligence data.

Do not change Coach behavior.

Do not begin Phase 2A UI rollout.

---

1. ESTABLISHED BASELINE

Treat the following as established:

- the deterministic Intelligence Foundation exists;
- it is local-first and read-only;
- it does not require a server adapter;
- no persistent Intelligence table exists;
- no persistent Intelligence profile/history exists;
- "intelligence.facts.server_adapter" remains OFF;
- all visible Intelligence flags remain OFF;
- Calora currently persists broad local state through a fixed AsyncStorage key;
- account-switch/shared-device state isolation has not yet been proven safe.

The purpose of this task is to close that local privacy gap and prepare the transient insight layer.

4. OBJECTIVE B — DEFINE THE ACCOUNT-LOCAL STATE IDENTITY

The local persistence namespace must derive from the authenticated identity that Calora already trusts.

Do not use:

- display name;
- email alone;
- client-generated arbitrary owner ID.

Use the stable authenticated identity already available from the Supabase session, or a safer existing canonical account identifier.

Document the chosen namespace source.

Conceptually:

calora_state:<stable_authenticated_user_identity>

The exact key format should follow repository conventions.

Do not expose sensitive identifiers unnecessarily in logs.

---

5. OBJECTIVE C — ACCOUNT-AWARE PERSISTENCE

Implement a safe account-aware persistence strategy.

Requirements:

- User A local data cannot hydrate into User B session.
- User B local data cannot hydrate into User A session.
- signing out must not leave User A’s active in-memory state visible;
- switching accounts must establish the new account namespace before hydration;
- anonymous/pre-auth state must be deliberately separated from authenticated state;
- stale account data must never be merged into the wrong account automatically.

Prefer namespacing over destructive deletion if Calora legitimately supports returning users on the same device.

Do not destroy prior account state merely because another account signs in unless product policy requires it.

---

6. OBJECTIVE D — SIGN-OUT SAFETY

Audit the exact sign-out flow.

When sign-out occurs:

1. stop current persistence writes;
2. clear active in-memory user state;
3. clear or detach user-specific transient state;
4. detach the current persistence namespace;
5. clear any user-specific query/cache state;
6. clear transient Intelligence state if any exists;
7. complete auth sign-out;
8. ensure the signed-out UI cannot render the previous user’s data.

Ordering matters.

Do not allow a final autosave after sign-out to write previous-user state into the next namespace.

---

7. OBJECTIVE E — ACCOUNT SWITCH SAFETY

Test direct account switching.

Scenario:

USER_A signs in
→ logs meals
→ changes planner
→ adds weight
→ saves recipe
→ signs out

USER_B signs in

Verify USER_B sees none of USER_A’s:

- food logs;
- profile/goals;
- weights;
- water/mood/activity;
- planner;
- shopping;
- recipes;
- reminders;
- health data;
- Coach history;
- living memory;
- sync state;
- derived Intelligence facts.

Then switch back to USER_A and verify USER_A state is restored only from USER_A’s own namespace if preservation is intended.

---

8. OBJECTIVE F — COLD START AND LEGACY MIGRATION

Existing users may already have state stored under the old fixed key.

Design a safe migration.

Determine:

- whether legacy local state can be confidently associated with the currently authenticated user;
- whether it should migrate once into that user’s account namespace;
- what happens when no authenticated user is available;
- how duplicate migration is prevented;
- how migration failure is handled;
- how rollback works.

Do not attach ambiguous legacy data to a new account automatically.

If ownership cannot be established safely:

LEGACY STATE OWNERSHIP: UNKNOWN

and use a conservative recovery strategy.

---

9. OBJECTIVE G — QUERY/CACHE ISOLATION

Inspect:

- TanStack Query cache;
- recipe API cache;
- any other runtime cache;
- Coach context/history;
- living memory;
- temporary drafts.

Confirm whether each is:

- global;
- account-scoped;
- screen-scoped;
- transient.

User-specific cache must be cleared or namespaced on account change.

Shared public/provider recipe data may remain shared if it contains no private user data.

Do not clear harmless shared caches unnecessarily.

---

10. OBJECTIVE H — LOCAL SECURITY TEST SUITE

Create permanent tests for:

- USER_A → sign out → USER_B;
- USER_A → USER_B → USER_A;
- account switching before hydration completes;
- sign-out during pending autosave;
- corrupted old persistence snapshot;
- legacy fixed-key migration;
- no-session startup;
- app restart with USER_A;
- app restart with USER_B;
- auth token refresh without account change;
- failed sign-out;
- storage write failure.

Verify no cross-account leakage.

11. OBJECTIVE I — TRANSIENT INSIGHT SELECTOR

Once local account isolation is proven, build a pure contextual-insight selector.

Recommended location:

artifacts/calora/lib/intelligence/

Potential file:

insightSelector.ts

The selector must consume existing Foundation facts only.

It must not query raw storage independently.

It must not fetch network data.

It must not persist output.

---

12. INSIGHT SELECTOR INPUT

Input should be structured Foundation output.

Conceptually:

facts
evidence
confidence
freshness
missingData
date/timezone

Do not pass arbitrary raw application state if Foundation facts already contain the required information.

The selector must be deterministic.

Same inputs must produce the same result.

---

13. INSIGHT SELECTOR OUTPUT

Use a structured transient result.

Conceptually:

ContextualInsight
- id/type
- category
- priority
- titleKey or structured message payload
- supportingFacts
- evidenceClass
- confidence
- freshness
- state
- reason
- generatedAt
- expiresAt if required

Possible states:

active
no_insight
insufficient_data
low_confidence
stale

Do not make prose generated by an LLM the data contract.

---

14. ALLOWED PHASE 1.9 INSIGHT TYPES

Keep the initial set narrow.

Allowed:

Current calorie status

Examples of deterministic meaning:

- substantially below configured target so far;
- near configured target;
- above configured target.

Avoid moral language.

Macro balance

Only where reliable targets and data exist.

Examples:

- protein remains materially below target;
- macro data incomplete;
- target already reached.

Meal distribution

Examples:

- majority of recorded calories concentrated in one meal;
- no breakfast log;
- no dinner log.

Do not infer “skipped meal.”

Use "not_logged".

Logging completeness

Examples:

- incomplete day;
- no logs;
- partial macro information.

Weight baseline

Only expose already-defined deterministic baseline facts.

Do not make health conclusions from them.

16. PRIORITY RULES

Implement a simple deterministic priority model.

The selector should favor:

1. data-integrity or missing-data warnings;
2. high-confidence significant current-state facts;
3. meaningful target deviations;
4. meal distribution;
5. lower-priority descriptive facts.

Avoid displaying five observations at once.

The selector should normally return one primary insight.

Optionally support a bounded secondary insight internally, but do not create a feed.

---

17. CONFIDENCE GATE

Do not produce an active contextual insight when confidence is inadequate.

Examples:

INSUFFICIENT
→ insufficient_data

LOW
→ low_confidence or no_insight depending on type

MEDIUM/HIGH
→ potentially eligible

Rules may vary by insight type.

A strong warning about missing data can itself be valid even when nutrition confidence is low.

---

18. FRESHNESS GATE

Do not use stale facts as current insights.

The selector must respect Foundation freshness and watermark semantics.

When relevant state changes:

meal added
meal edited
meal deleted
target changed
timezone changed

the previous transient output must no longer be treated as current.

Because no insight is persisted, recomputation from updated facts should naturally replace it.

---

Create tests specifically for this.
