## Executive result

The current source has a comparatively strong application-level backend control set: bearer identity is resolved server-side from Supabase Auth; route data access is keyed to the verified identity; deletion fences prevent writes during erasure; expensive routes use persistent atomic rate limits; paid-provider paths fail closed when the limiter is unavailable; provider calls have bounded abort timeouts; migrations are forward-only and separated from API startup; database TLS and a dedicated migration credential are implemented; startup readiness checks the database and limiter table before opening a listener; health/liveness endpoints are explicit; and logs are sanitized.

This is **not sufficient for a full US commercial-launch PASS** for the backend domain. The canonical Calora domain schema is in a separate managed PostgreSQL database, while the configured Supabase project contains no Calora application tables. Therefore Supabase RLS evidence does not prove isolation of actual Calora data, and the managed PostgreSQL production database's database-level policy/grant posture was not independently inspected in this bounded audit. The repository intentionally states that the API is the sole data path and uses application-level ownership predicates rather than RLS. The historical Supabase report explicitly says the required two-user RLS tests were blocked. Live Railway variables, live migration state, live storage behavior, live observability, and current production rollback/recovery execution were not re-run here.

## Key evidence details

### Route/auth boundary
`artifacts/api-server/src/app.ts` sets a single trusted proxy hop, HSTS, strict origin rejection/CORS, JSON size limit, structured HTTP logging, and a generic sanitized error handler. `supabase-auth.ts` disables client persistence on the server verifier, verifies the bearer token against Supabase Auth, checks the deletion fence, and returns only server-derived identity fields. The server never trusts a caller-supplied user ID for normal domain operations.

Representative cross-account evidence is in `artifacts/api-server/src/__tests__/tenant-isolation.integration.test.ts`: User B cannot list or delete User A's diary row by guessed ID; sync upserts/deletes are scoped to the verified identity; and a foreign capture session cannot be consumed. The test is `describe.skipIf(!RUN_DB_INTEGRATION_TESTS)` and therefore requires explicit `CALORA_RUN_DB_INTEGRATION_TESTS=true` plus a database URL. This matters: the test exists and is well targeted, but it is not proof that it ran against current production.

### Database ownership and the RLS blocker
`lib/db/src/schema/index.ts` defines the Calora tables and `lib/db/migrations/0001...0020` is the migration authority. The Supabase security report identifies project `pzdulhkpwbrbrgskwwwe` as active but states that it contains no Calora application tables; the actual domain schema is in a separate managed PostgreSQL database. It also records `Supabase RLS / two-user tenant tests: BLOCKED` and says database-level tenant isolation remains unverified in the database that actually stores Calora data.

This is classified **FAIL** for launch certification, not PASS or merely historical BLOCKED, because the requirement is actual backend data isolation evidence for the system that stores customer data. The explicit absence of RLS is an architectural choice and route tests reduce risk, but no independently verified database-enforced boundary was found. The remediation needed before launch is either (a) implement and independently test database-level tenant isolation in the managed PostgreSQL design, or (b) provide an approved security architecture exception with production role/grant review, adversarial two-user testing, and compensating controls accepted by the certification owner. No such current exception was found in the inspected evidence.

### Infrastructure and release controls
`artifacts/api-server/src/index.ts` refuses to listen until database readiness and the capture limiter table are available, and it shuts down with a bounded 20-second graceful timeout. `.github/workflows/database-integration-postgres.yml` runs fresh-schema PostgreSQL 16 integrations; `.github/workflows/release-validation.yml` checks source provenance, generated clients, migration smoke tests, dependency audit, release attestation, typecheck, complete tests, and production artifact builds. These are strong repository controls but do not prove the present Railway environment, present database schema, present storage bucket, or present alerting configuration.

### Current test execution boundary
No source mutation or deployment was performed. The attempted local API test invocation was not accepted by the sandbox execution wrapper because it rejected the repository as a webdev working directory; consequently no fresh API suite result is claimed here. The report relies on current source inspection, test definitions, CI workflow definitions, and historical reports with their stated dates and environment assumptions. This is intentionally conservative and does not infer PASS from historical claims.

## Critical blockers for full commercial launch

1. **Actual managed-PostgreSQL tenant isolation is not independently certified.** The Supabase project has no Calora tables/RLS, and the database that does hold Calora data was not inspected for live grants, roles, policies, or adversarial isolation in this audit.
2. **Current production configuration is not re-attested.** Railway deployment identity, environment variables, migration journal state, database target, storage bucket policy, provider timeout values, and observability/alert routing were not read or verified in the current environment.
3. **Current production rollback/recovery is not demonstrated.** Existing runbooks and synthetic/non-production tests are not a current production database restore, storage restore, or rollback drill.
4. **Fresh backend test execution was not completed in this sandbox.** Integration tests are explicitly gated and the command wrapper blocked execution from this repository context; no fresh pass count is asserted.

## Recommended certification disposition

**Backend/infrastructure domain: NO-GO for full US commercial launch pending closure of B04 and the blocked live-environment attestations.** The application controls are promising and many are covered by focused tests, but the launch decision must not treat repository intent, historical Railway health, or Supabase security findings as proof of present production safety.
