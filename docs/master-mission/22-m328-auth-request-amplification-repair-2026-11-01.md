# Mission 328 — Calora Auth Request Amplification Root-Cause Repair

Date: 2026-11-01
Scope: Authentication request amplification investigation and source repair. No production deployment, database change, credential change, billing change, native build, or app-store action was performed.

## Final verdict

**PASS FOR PROTECTED DELIVERY / NOT YET DEPLOYED.**

The repair is narrowly scoped, fail-closed, and validated by the complete client and API offline suites. Production Supabase usage must be re-measured after a separately authorized deployment; this mission does not claim that the monthly egress overage is already resolved.

## 1. Root cause

The dominant `/auth/v1/user` traffic is generated by the API server's authenticated-request verifier in `artifacts/api-server/src/lib/supabase-auth.ts`. Every API request carrying a bearer token called `supabase.auth.getUser(token)`, which performs a network verification against Supabase Auth. The prior quota investigation recorded 31,297 successful `GET /auth/v1/user` responses in the available 24-hour Calora log window, including separate hourly bursts of 7,785, 6,465, 3,775, and 3,682 requests. Only 45 token-exchange requests were observed in the same aggregate.

This evidence identifies repeated authenticated API traffic and per-request server verification as the amplification boundary. It does not prove that every request came from one browser, nor does it provide byte-level attribution; Supabase's accessible log interface does not expose response sizes. The implementation therefore avoids unsafe long-lived token caching.

The client also had multiple concurrent token consumers that could call `supabase.auth.getSession()` at the same time. These reads are normally local session-storage operations and are not themselves equivalent to `/auth/v1/user`, but they created avoidable bootstrap contention and refresh races.

## 2. Implemented repair

### Server-side verification deduplication

`verifyBearerToken` now:

- hashes the bearer token with SHA-256 solely as an in-memory map key;
- shares only the currently in-flight verification promise for identical concurrent tokens;
- removes the promise immediately when it settles, whether fulfilled or rejected;
- retains the existing server-side Supabase verification, account-deletion fence, metadata eligibility checks, and fail-closed error behavior;
- never stores a verified user or token after the request-level verification settles.

No token, user record, or authorization result is logged or persisted by the repair.

### Client-side single-flight token acquisition

`getFreshAccessToken` now shares one in-flight session read/refresh promise among concurrent consumers. The promise is cleared in `finally`, so logout, token expiry, revocation, and account changes are not hidden behind a stale cache.

## 3. Request-count evidence

The isolated client regression starts two concurrent token consumers while the session read is pending and observes exactly one `getSession()` call, with both callers receiving the same token.

The isolated server regression starts two concurrent requests with the same bearer token while `auth.getUser()` is pending and observes exactly one Supabase verifier call. A sequential second request after settlement performs a new verification, proving that the repair is in-flight deduplication rather than an authorization cache.

These are deterministic isolated counts, not production traffic measurements.

## 5. Security and behavior preservation

The repair does not bypass JWT verification, trust client-supplied user IDs, weaken account deletion fencing, broaden authorization, alter RLS, modify Supabase settings, or retain authorization results after settlement. Auth failures continue to fail closed. Different tokens use different in-flight keys. A rejected verifier promise is removed and can be retried by a later request.
