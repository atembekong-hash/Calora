Mission

Expand the existing Calora Recipes tab into a three-part recipe system while preserving the current working implementation.

The new Recipes architecture must contain:

Discover | Premium | Create

The current open-source recipe experience becomes Discover.

A new Premium section will use a higher-quality paid recipe API.

A new Create section will allow users to generate personalized recipes with AI using Calora data such as shopping-list items, available ingredients, meal-plan context, recent foods, nutrition targets, manually entered ingredients, and other available signals.

This is an expansion of the existing Recipes system. It is not a request to rebuild the tab from scratch.

Proceed cautiously.

---

1. Mandatory first step: inspect before editing

Before making changes:

- Inspect the complete current Recipes implementation.
- Identify all relevant screens, components, hooks, services, API clients, state management, caching, navigation, database tables, schemas, nutrition logic, bookmark logic, search logic, filters, recipe-detail screens, shopping-list integrations, meal-plan integrations, logging integrations, and shared UI components.
- Identify the current open-source API integration and how its data is transformed.
- Identify anything already implemented for recipe creation, saving, meal logging, shopping lists, meal planning, scanning, nutrition calculations, user preferences, dietary restrictions, allergies, recent foods, and user goals.
- Map dependencies before changing them.
- Reuse existing working systems wherever reasonable.
- Do not replace working architecture merely because another implementation would be easier.

Produce an internal implementation map first.

Do not begin broad modification until the current system is understood.

Discover | Premium | Create

Do not add new bottom-navigation tabs.

- "Discover" opens the current open-source experience.

7. Do not confuse “premium source” with subscription status

Treat recipe-source quality and Calora subscription entitlement as separate concerns.

The architecture must not assume that every recipe from the paid API is necessarily locked behind a Calora subscription.

Create a clean entitlement point so access rules can later be configured without rewriting Premium.

Do not introduce a paywall unless the existing product rules already require it.

8. Create section

Build a dedicated personalized recipe-generation experience.

The opening Create screen should stay simple.

Header:

Primary starting modes:

2. Match my goals

These modes should feed one common recipe-generation engine.

Do not create four unrelated implementations.

12. Surprise me

13. Two-stage AI generation

Do not generate a full detailed recipe immediately after every request.

Use a two-stage workflow.

Stage 1: Generate recipe concepts

Return approximately three concise options.

Each option should contain enough information to choose intelligently.

Example:

Lemon chicken couscous
28 min · 590 kcal · 48 g protein
Uses 8 of 9 selected ingredients

Chicken spinach skillet
21 min · 525 kcal · 51 g protein
Uses 7 selected ingredients

Spiced chicken rice
32 min · 635 kcal · 44 g protein

Stage 2: Generate full recipe

Only after the user selects an option should Calora generate or finalize the complete recipe.

This architecture is important for:

- Lower AI cost
- Lower latency
- Less wasted generation
- Better user choice
- Easier retries

Do not bypass this without a strong technical reason.

14. Canonical recipe model

This is a critical architectural requirement.

Do not create separate incompatible recipe models for Discover, Premium, and Create.

Normalize all recipe sources into one canonical internal Calora recipe representation.

A conceptual model should support fields such as:

Recipe {
  id
  sourceType
  sourceProvider
  sourceId

  title
  description
  image

  cuisine
  mealTypes
  dietTags

  servings
  prepTime
  cookTime
  totalTime

  ingredients[]
  instructions[]

  nutrition
  allergens[]
  equipment[]
  difficulty

  nutritionConfidence
  nutritionSource

  isSaved
  createdByUser

  createdAt
  updatedAt
}

Adapt this to the current project architecture and database conventions.

Do not blindly copy this exact shape if an existing recipe model already exists.

Extend and normalize the existing model where safer.

Expected "sourceType" values should support at least:

- "open"
- "premium"
- "calora_ai"

Design so future values can be added, such as:

- "user_created"
- "imported"

15. Recipe provenance

Every recipe must retain clear provenance internally.

Record:

- Source type
- Provider
- Provider recipe ID when available
- Whether nutrition came from provider data, Calora calculation, or another verified nutrition source
- Whether nutrition remains unverified or approximate

Do not erase source provenance after normalization.

The UI should expose source information when relevant.

---

16. AI must not invent authoritative nutrition

This is mandatory.

AI can generate:

- Recipe concepts
- Ingredient combinations
- Ingredient quantities
- Instructions
- Descriptions
- Substitutions
- Cooking ideas

Do not treat AI-generated calorie or macro numbers as authoritative.

After AI produces the structured ingredient list and quantities, pass those ingredients through the existing Calora nutrition system or an appropriate structured nutrition-data service.

Example:

150 g chicken breast
100 g cooked rice
80 g spinach
10 g olive oil

Then calculate:

- Calories
- Protein
- Carbohydrates
- Fat
- Fiber
- Available micronutrients

Store nutrition provenance and confidence.

If precise nutrition cannot be calculated, communicate that clearly.

Never disguise estimates as verified values.

---

17. Allergens and dietary restrictions

Use structured ingredient data to validate known allergens and dietary restrictions where possible.

AI may assist in interpreting the recipe, but do not rely solely on AI-generated allergen claims.

If confidence is insufficient, communicate uncertainty.

Existing user allergy and dietary settings should be respected throughout Create.

Do not suggest clearly incompatible recipes when reliable restriction data exists.

19. AI recipe editing

Support common modifications such as:

- Make it higher protein
- Reduce calories
- Make it vegetarian

- Remove dairy

- Recalculate nutrition.
- Re-evaluate allergens and dietary compatibility.
- Preserve unchanged recipe details where reasonable.

Do not merely change the displayed calorie number with AI.

- Loading states
- Empty states
- Error states
- Retry behavior
- Caching
- Image loading
- Pagination/infinite loading
- Debounced search
- Request deduplication
- AI generation timeout handling

26. AI generation states

Create clear states for AI recipe generation.

At minimum:

- Idle
- Preparing request
- Generating concepts
- Concepts available
- Generating full recipe
- Calculating nutrition
- Recipe ready
- Generation failed
- Nutrition calculation failed

Do not show fake progress percentages.

Use truthful status text.

Allow retry after recoverable errors.

Preserve the user's request after an error.

---

27. Offline and degraded states

If the device is offline:

- Existing cached/saved recipes should remain usable where possible.
- Clearly communicate that new API searches or AI generation require connectivity.
- Do not crash.
- Do not show an empty blank screen.

If the premium provider fails:

- Discover should continue working.
- Create should continue working if its required services remain available.

Providers should fail independently.

28. Security and privacy

Do not expose private API keys in the client bundle.

Premium recipe API secrets and AI provider credentials must remain server-side or within the project's existing secure backend architecture.

Do not send unnecessary user data to external recipe providers.

When AI generation uses personal context, send only the minimum fields required for the current request.

Respect existing authentication and user-data boundaries.

Do not weaken row-level security or authorization rules.

33. Implementation order

Execute in controlled stages.

Phase 1: Discovery and architecture

- Inspect existing implementation.
- Produce dependency map.
- Identify reusable components and data models.
- Determine migration needs.
- Determine premium provider integration boundary.
- Determine AI generation backend boundary.

Validate before editing.

Phase 2: Internal Recipes navigation

Implement:

Discover | Premium | Create

Move current experience under Discover without regression.

Test.

Phase 3: Canonical data layer

Normalize current recipe data into the common recipe model.

Preserve backward compatibility.

Add migrations only if required.

Test current Discover thoroughly.

Phase 4: Premium provider

Implement premium-provider service abstraction.

Connect actual provider configuration if credentials already exist.

If credentials are absent, build the provider boundary and clearly report what credential/configuration is required rather than inventing values.

Build Premium UI, search, loading, errors, and filters.

Test.

Phase 5: Create foundation

Implement:

- Use what I have
- Match my goals
- Tell Calora
- Surprise me

Connect available existing Calora data.

Test.

Phase 6: Two-stage AI generation

Implement:

Request → concepts → user selection → complete recipe.

Test generation failures and retry.

Phase 7: Structured nutrition calculation

Connect generated ingredient quantities to the existing nutrition system.

Validate calculations.

Store nutrition provenance.

Phase 8: Cross-feature integrations

Connect:

- Saved Recipes
- Shopping List
- Meal Plan
- Food logging

Test each independently.

Phase 9: Recipe editing

Implement modifications and nutrition recalculation.

Test all major modification paths.

Phase 10: Full validation

Run real-user flow validation across all three sections.

35. Acceptance criteria

The task is complete only when:

1. Recipes contains functional Discover, Premium, and Create sections.
2. Existing Discover functionality has not regressed.
3. All recipe sources normalize into one common internal recipe system.
4. Recipe provenance is preserved.
5. Premium data uses an isolated provider abstraction.
6. AI Create supports personalized Calora context.
7. AI generation uses the concept-first workflow.
8. AI-generated recipes have structured ingredients and instructions.
9. Nutrition is calculated through structured nutrition data rather than blindly trusted AI estimates.
10. Recipes can interact correctly with Saved Recipes.
11. Recipes can interact correctly with Shopping List.
12. Recipes can interact correctly with Meal Plan.
13. Recipes can be logged into nutrition tracking.
14. Recipe edits trigger appropriate nutrition recalculation.
15. All loading, empty, offline, and failure states are handled.
16. No API secrets are exposed client-side.
17. Dark and light themes work.
18. Layout is stable on Android and iOS phone sizes.
19. No current working feature is broken.
20. No production build is triggered.
